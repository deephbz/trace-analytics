Why an agent waits: the physics of LLM speed, from one token to compaction

An interactive primer for readers who know physics and computer science but not LLM internals · trace-analytics research ·

A coding agent spends much of its time waiting for a model. The wait has a structure. Kernels, chips and model shapes differ a lot, but they all fit one small set of physical limits: how fast a chip can move bytes, and how fast it can multiply numbers. This page builds that picture step by step. Each step adds one idea and one demo.

The demos run on a toy machine. Use the machine panel in the corner to choose a chip, how many chips serve one copy of the model, and a model shape. The chip figures come from public spec sheets and are rounded. The model shapes are public open-weight designs; the frontier models behind your subscriptions keep their shapes private. Trust the shapes of the curves more than the absolute numbers.

1A language model writes one token per pass

A token is a piece of text, on average about ¾ of an English word. The model is a fixed function. It reads the whole context and returns a probability for every possible next token. The server picks one token, appends it to the context, and calls the function again. Text comes out one token per pass, because each pass needs the token before it.

Physicists can read this as an iterated map: x(t+1) = f(x(0..t)). Ordinary decoding confirms one token per pass, because step t+1 needs the token from step t. Speculative decoding guesses several tokens cheaply and checks them in one pass, so it can confirm several tokens per pass; its gain depends on how often the guesses are right. The chain stays serial. This is the first law of agent speed.

Grey tiles are the prompt. Each pass reads the context and emits one coloured tile, which joins the context for the next pass.

2Each pass reads every active weight from memory, and memory is the slow part

The function f is mostly matrix multiplication. Its matrices hold the weights: tens to hundreds of billions of numbers. For one pass that produces one token, the chip must stream every weight that the pass uses from memory into its compute units. Each weight then takes part in about two arithmetic operations (one multiply, one add).

A modern chip can do several hundred operations in the time it moves one byte. Two operations per byte leaves the compute units idle most of the time. Decoding is therefore memory-bound: the time per token is about the bytes of weights divided by memory bandwidth.

time per token ≈ bytes of active weights ÷ memory bandwidth
Left: memory, one row per layer. Each sweep reads all active weights for one token. The animation runs slower than real time; the readout shows the real figures for the machine in the panel. Weights are stored as 8-bit numbers (1 byte each). Try the wafer: Cerebras keeps the weights in on-chip SRAM, which moves bytes thousands of times faster than the stacked DRAM (HBM) next to a GPU. One wafer holds only 44 GB, so the panel shows a warning when the weights do not fit; the toy does not model the links between wafers.

Two design choices change the byte count. A dense model uses every weight for every token. A mixture-of-experts (MoE) model splits most weights into many "experts" and sends each token to a few of them. The public DeepSeek-V3 design has 671B weights in total but uses only about 37B per token. That is why large MoE models can decode fast. Section 5 shows the catch.

Several chips can share one copy of the model. Each chip then holds and reads a slice, so their bandwidths add up. They must also exchange results at every layer, and that adds a small fixed delay per pass. With enough fast memory, that fixed delay becomes the limit: the readout then says latency-bound. Real servers fight it with fused kernels and by decoding several guessed tokens per pass.

3Reading the prompt runs in parallel, so input is cheap and output is dear

The prompt is different. All prompt tokens are known before the model starts, so the chip can push all of them through each layer at once. One read of a weight now serves thousands of tokens. This phase is called prefill. With a long prompt it does many operations per byte, so the arithmetic units, not memory, set its speed: it is compute-bound. A short prompt still has to read every weight once, so a prefill of a few tokens is memory-bound like decode. The token-by-token phase from section 2 is called decode.

Both lanes produce 8 tokens. Prefill reads the weights once for all 8. Decode reads them 8 times, one token at a time.

The roofline plot below is the standard way to see this. The x-axis is arithmetic intensity: operations per byte moved. Below the ridge point, memory bandwidth sets the speed. Above it, compute sets it. Decode sits far left. Prefill of a long prompt sits far right.

Log-log axes. The flat roof is the chips' peak arithmetic rate; the sloped roof is bandwidth × intensity. The timing demos assume 50% of peak in decode and 40% in prefill. These efficiencies are illustrative.

This gives the first client-side law. On GPU serving, a long prefill processes input tokens far faster than decode emits output tokens; the ratio depends on context, batch, hardware and caching. Your compaction benchmark agrees: wall time followed output length with R² , and context size explained almost none of it (R² ).

4Attention keeps a memory of every token, so long context slows each step

So far each pass read only the weights. The model also needs to look back at earlier tokens. The mechanism is attention: for every past token the model keeps two vectors, a key and a value, and each new token compares itself with all of them. The stored vectors are the KV cache. It grows by a fixed number of bytes per token of context.

Each decode step must read the whole KV cache, so its bytes add to the weight bytes from section 2. The toy stores each KV element in one byte. At that precision, 100k tokens of context use 16.4 GB of KV cache for the dense 70B model, about 23% of its 70 GB of weights; 16-bit storage doubles it. Prefill pays too: every prompt token compares itself with every earlier one, so attention work grows as N². That is quadratic attention.

Linear attention and state-space layers replace the growing cache with a fixed-size state, so each step costs the same at any context length. Many recent models are hybrids: their full-attention layers keep a growing cache, so their cost still grows with context, only more slowly. The dashed curve below is a model built entirely from fixed-state layers. Other tricks shrink the cache without removing it: sharing keys across heads, compressing them, or attending only to a recent window.

Each new token (right) reads every stored key and value (quadratic), or one fixed state (linear). The bar under the tiles shows bytes read per step: weights in purple, KV cache in orange.

5Many users share one weight read, and the provider chooses your speed

Section 2 had one user per pass. Providers put many users' tokens in the same pass: a batch. One read of the weights now serves the whole batch, so the chip produces far more tokens per second in total. Each user's KV cache is private, though, so its bytes add up. Past some batch size the compute units fill, and every extra user slows everyone.

The provider picks the batch size. A large batch gives cheap tokens and a slow stream for each user. A small batch gives a fast stream at a higher price per token. Providers trade throughput for speed with batch size, chips per copy, kernels and other optimisations. A "fast mode" buys lower latency; which of these levers it pulls is usually not disclosed.

Blue: tokens per second for one user. Grey: tokens per second for the whole batch. Both use the panel's machine.

Now the MoE catch. One token uses 8 of 256 experts. In this toy, each token picks its 8 experts uniformly and independently. A batch of 64 tokens then touches about 87% of the experts on average. Real routing is skewed and correlated, but the direction holds. At large batch an MoE model reads almost all of its weights every pass, like a dense model of its full size. Its per-token arithmetic stays small, though.

256 experts. Each token of the current batch lights the 8 experts it uses. The expected fraction lit under uniform routing is 1 − (1 − 8/256)B. Choose the MoE model in the panel to see it change with batch size.

6A cache hit skips the prefill, not the decode

An agent sends almost the same context again on every turn: the old conversation plus a few new messages. The KV cache from section 4 is exactly the result of prefill. The provider can keep it and reuse it when the next request starts with the same prefix. This is the prompt cache. A hit removes the prefill work for the cached prefix. The new tokens still need prefill, and every output token still needs a full decode step.

The time to first token (TTFT) therefore splits into a fixed floor (network, queue, routing, cache lookup) plus prefill of the uncached tokens. Prices follow the work. A cached input token costs about a tenth of a fresh one, and an output token costs several fresh ones.

TTFT ≈ floor + prefill(uncached tokens | cached prefix)
cost ≈ uncached × p_in + cached × p_cache + output × p_out
Green: the cached prefix, loaded at once. Orange: uncached tokens, prefilled at the panel machine's rate. The floor is fixed at 0.5 s here. Prices are the claude-sonnet-5-5 list prices used in the benchmark report: $2 input, $0.20 cache read, $10 output per million tokens.

7What the client sees: TTFT, decoding, and stalls

A client sees a stream of chunks with timestamps. trace-analytics splits each request's wall time into five parts:

  • TTFT floor: the shortest first-token wait the route ever shows.
  • TTFT variance: the rest of the first-token wait (queue, prefill, cache misses).
  • decoding: output tokens at the steady stream rate.
  • stall during decoding: gaps inside the stream.
  • stall after last token: time between the last token and the end of the response.

One known cause of gaps is sharing. When a new request joins a busy server, its prefill competes with the decode streams for the chip. Servers cut long prefills into chunks to limit this interference. Some servers move prefill to separate chips (disaggregation), which removes the shared-compute contention but adds a transfer of the KV cache. Client timestamps show the gaps, not their cause, and the client cannot see which design a route uses.

8Compaction is one more request, so the same laws set its cost and wait

When the context nears the window limit, the agent compacts it. A model writes a shorter replacement, and the session continues from that. The rest of this page applies directly:

  • Wait ≈ TTFT + output ÷ effective output rate. The summary is output, so its length sets most of the wait (sections 2 and 3).
  • Cost: pi's native compaction sends a new summarizer prompt, so it pays fresh-input price for the whole history. An in-session method continues the cached conversation and pays the cache price (section 6).
  • Carry: every later turn reads what compaction leaves, at the cache price. A larger leftover costs a little on each turn and brings the next compaction sooner.

Your benchmark agrees with the wait law on its two routes. On both models one straight line in output tokens fits all methods. Its slope is an effective seconds-per-output-token rate for these runs; it includes any overhead that grows with output.

The cost law shows best over a whole session. The demo grows the context by a fixed amount per turn and compacts at the threshold. It compares the two cost models from the benchmark. Every turn also pays to read the context at the cache price.

9What a client can rely on

Each law below states what it holds for and its evidence. measured means your own logs or benchmark show it. standard means it follows from the physics above and published systems work, but these logs do not isolate it. provisional means it is plausible and unverified.

10Limits of this page

  • The toy machine ignores many real effects: kernel efficiency, network hops, speculative decoding, quantization below 8 bits, shared prefixes between users, and scheduling policy. Its utilisation (50% decode, 40% prefill) and per-layer sync delay are assumptions. It shows directions and orders of magnitude.
  • Chip figures are rounded public numbers: H100-class 80 GB, 3.35 TB/s and about 1 PFLOP/s dense 16-bit; B200-class 180 GB, 8 TB/s and 2.25 PFLOP/s; Cerebras WSE-3 44 GB of SRAM at 21 PB/s and 125 PFLOP/s (vendor figure). At 1 byte per weight the 671B model needs at least 16 wafers and the 70B model 2. The toy sums bandwidth across chips and ignores the links between wafers, so it does not predict a real Cerebras deployment.
  • Frontier models (claude-sonnet-5-5, gpt-6.1-sol) do not publish their shapes. Their measured decode speeds (about 136 and 37 tokens per second in the benchmark) include all the choices above, and the client cannot separate them.
  • The benchmark data are 63 compactions on 9 slices per model. See ../compaction-bench/report.html.
